# Инструкции для агентов разработки

## Цель

Создать удобное Windows-приложение для обычных пользователей по требованиям в `docs/PRODUCT_SPEC.md`. Пользовательский результат важнее технической демонстрации. Работоспособность прототипа или алгоритма не равна готовности продукта.

## Порядок работы

1. Прочитать README, спецификацию, архитектуру, план задач и критерии приёмки.
2. Проверить фактическое состояние кода; документация описывает целевое состояние, а не выполненную работу.
3. Выбрать ограниченную задачу из ROADMAP с учётом зависимостей. Не помечать её завершённой до выполнения критериев.
4. Изменять код, тесты и затронутую документацию согласованно. В отчёте указать результат, выполненные проверки и ограничения.
5. Не запрашивать повторное согласование рутинных решений в рамках спецификации. Противоречия, изменения пользовательского поведения и существенные изменения стека сначала явно описать.

## Обязательные ограничения

- Исходные файлы меню не изменять. Создавать независимые результаты.
- Сохранять блюда, формулы, стили, объединения, размеры, параметры печати и прочее содержимое вне явно изменяемой даты.
- Проверять реальное сохранение и повторное чтение XLSX; одного успешного вызова экспорта недостаточно.
- Не вычислять новые значения для несвязанных формул и не удалять их кэш без необходимости.
- Не угадывать незаметно порядок пяти меню. Всегда показывать распределение по дням и позволять его исправить.
- Не привязывать приложение навсегда к J1: это начальная настройка для известного шаблона, нужна возможность выбора листа и ячейки.
- Не зашивать даты октября 2026 года в производственную логику. Примеры из задания использовать только как тестовые данные.
- Не публиковать реальные меню школы, личные пути, настройки, ключи или токены.
- Данные пользователя хранить отдельно от каталога установки. При обновлении сохранять настройки и шаблоны.
- Не требовать Excel, Python, SDK или PowerShell-команд от конечного пользователя.
- Не заменять системное напоминание таймером, который работает только при открытом окне.
- Не обещать уведомление на выключенном компьютере или принудительный обход запрета уведомлений Windows.
- Не утверждать, что релиз существует, пока его файлы не опубликованы и не проверены.
- Кнопка «Проверить обновления» и установка новой версии из GitHub Releases входят в первый релиз. Не заменять их одной ссылкой на сайт. Скачивать и запускать установщик только после нажатия пользователем «Установить», проверять совместимость и целостность файла; сохранять пользовательские данные.

## Работа несколькими агентами

Если координирующий пользователь поручил параллельную разработку: заранее согласовать владельцев модулей, интерфейсы и зависимости задач. Ядро, UI, уведомления и сборку можно разделять после фиксации контрактов. Не редактировать одновременно одни и те же файлы без координации. Завершение части не означает завершение интеграции.

## Проверки

Следовать `docs/ACCEPTANCE.md`. После появления решения добавить сюда точные команды сборки и тестов, проверенные в репозитории. Не выдумывать несуществующие команды. Для UI и уведомлений нужны проверки на Windows; прохождение модульных тестов их не заменяет.

Проверенные команды этапа 1 (Windows, SDK из global.json):

```powershell
./scripts/Build.ps1
./scripts/Build.ps1 -Capture
```

Первый сценарий собирает решение и запускает 15 синтетических проверок консольного стенда `experiments/MenuWidget.Probes`; второй также отрисовывает семь экранов в `docs/design`. Это ещё не полноценный набор тестов продукта. Текущие ограничения и следующий шаг — `docs/STAGE_1.md`. Не считать интерфейсный макет рабочей реализацией UI-сервисов.

## Документация и отчёты

Пользовательские тексты писать по-русски, понятными словами. Сохранять ясные состояния пустых комплектов, ошибок и успешного экспорта. Не маскировать ошибки сообщением об успехе. Невыполненные проверки явно отмечать.
