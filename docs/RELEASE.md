# Сборка и публикация

## Цель

Пользователь получает одну ссылку, скачивает установщик и запускает приложение через ярлык. Исходный код, SDK и команды ему не нужны.

## Репозиторий

https://github.com/kuzmin-lemmi/MenuWidget

Не включать реальные школьные меню, локальные пользовательские файлы, ключи подписи, токены и настройки. Синтетические примеры должны быть явно обозначены.

## CI и версии

После появления решения добавить GitHub Actions:

1. Pull request и изменения основной ветки: восстановление зависимостей, сборка и автоматические тесты на Windows.
2. Тег `vX.Y.Z`: повторить проверки, собрать self-contained приложение и установщик, рассчитать SHA-256, сгенерировать манифест обновления и подготовить GitHub Release.
3. Публиковать только если все необходимые задания успешны. Упаковку и публикацию выполнять с минимальными разрешениями; секреты не передавать недоверенным PR.
4. Перед публичной публикацией установить именно полученный артефакт на чистую Windows и пройти smoke-проверки из ACCEPTANCE.

На этапе 1 добавлен `.github/workflows/build.yml`: сборка решения, синтетические проверки и артефакт интерфейсного прототипа для Windows x64. Это не workflow публикации релизов. Теги, установщик, манифест и публикация GitHub Release пока не подключены. Проверенные команды — в `docs/STAGE_1.md`; SDK закреплён в `global.json`.

## Состав релиза

- `MenuWidget-Setup.exe` — установщик для заявленной архитектуры; сначала Windows x64. Другие архитектуры выпускать только после проверки.
- Контрольные суммы SHA-256.
- `update-manifest.json` — машиночитаемые версия, поддерживаемые ОС, архитектура, точное имя установщика и SHA-256. Версия совпадает с тегом и версией приложения; схема фиксируется и проверяется CI до публикации.
- Короткая инструкция по установке, двум комплектам, настройке цикла и воскресного времени.
- Скриншоты реальной версии.
- При необходимости архив синтетических примеров.
- Release notes: версия, изменения, поддерживаемые Windows, известные ограничения и статус подписи.

Не прикреплять незавершённые артефакты под видом готового установщика. Решение о лицензии репозитория принимает владелец; агент не назначает лицензию самовольно.

## Последовательность публикации

1. `v0.1.0` — prerelease для ограниченной проверки. Не считать его стабильной версией.
2. Проверить установку, обработку файлов, напоминания, обновление и удаление; собрать обратную связь.
3. Исправить ошибки, пройти приёмку и выпустить `v1.0.0` как стабильный релиз.
4. Проверить страницу и скачивание со стороны пользователя.

## Ссылка для распространения

Постоянная ссылка после стабильной публикации:

https://github.com/kuzmin-lemmi/MenuWidget/releases/latest

Для первой тестовой версии делиться прямой ссылкой на её prerelease: `latest` не предназначен для ссылки на единственный prerelease.

GitHub Releases позволяет прикладывать установщики и описание версии: [документация GitHub](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

## Подпись и обновления

Проверить возможность цифровой подписи установщика. Не обещать отсутствие предупреждений Windows у неподписанной сборки; фактический статус указывать в инструкции. Секреты подписи хранить вне репозитория.

В первом релизе обязательно работает кнопка «Проверить обновления» с последующей установкой из программы. По запросу пользователя приложение находит новую стабильную версию в этом репозитории, показывает изменения и после нажатия «Установить» скачивает, проверяет и запускает совместимый установщик. Фоновая установка без действия пользователя не предусмотрена.

Каждый стабильный релиз должен содержать совместимые установщик и манифест. Не переименовывать опубликованные артефакты без учёта клиентов. Поддерживать версионирование схемы манифеста. Обновление нельзя объявлять работающим до испытания перехода между двумя собранными установленными версиями; тестовые данные API не заменяют такую проверку. Не публиковать фиктивные стабильные релизы ради тестов.

Сохранность настроек, шаблонов и готовых файлов, корректное завершение приложения, обработка отказа в повышении прав, откат при неудаче и запуск новой версии входят в приёмку. Выбор установщика должен учитывать этот сценарий с начала разработки.
